# 子代理吃不吃得到 mod 的 prompt.compose — 2026-10-03 的量測：(a) 無效，控制組三次失敗

這一頁記錄 `docs/90-agent/plans/2026-10-03-mod-probe-design.md` 四項實測裡實際跑完的部分。結論先講：(a)「子代理吃不吃得到 `prompt.compose` 改的 system prompt」判「無效」，不是「否」。設計第 3 節規定，主 session 的正控制組（問它系統提示裡有沒有 `MOD-PROBE-COMPOSE-` 開頭的一行）若答錯，連主 session 都沒吃到，子代理沒吃到就不說明任何事。這個控制組跑了三次，三次主 session 都答「沒有」。跑一次就不再更新。

## 方法

一個一次性的 mod（`evidence/2026-10-03-mod-probe/probe.ts`、`hooks.json`、`tsconfig.json`）掛在 `prompt.compose` 上，加入兩個段：`fankeel-mod-probe:marker-shared`（shared 區段）與 `fankeel-mod-probe:marker`（session 區段），內文含 nonce `MOD-PROBE-COMPOSE-<uuid>`。每次 hook 觸發都寫一個 JSON 檔（`$.fs.write` 只能整檔寫入，所以一事件一檔），共 353 個，原樣放在 `evidence/2026-10-03-mod-probe/records/`。第二、三次重跑時儀器又加了 `compose.final`（探針自己呼叫 `$.prompt.compose()` 的結果）、`prompt.compose.after`（hook 鏈跑完之後的 `idsReturned` 與每段文字）與 `prompt.section`。

## 結果

- 標記進了 hook 鏈：第三次重跑（`session.start` 記錄時間 1791005998828 之後）的 `compose.final` 5 筆，ids 都含兩個標記，`hasSession`、`hasShared` 皆為 true；真實的 `prompt.compose.after`（例如 `1791006024604`）`idsReturned` 共 13 段、含兩個標記，`texts` 末段是 `MOD-PROBE-COMPOSE-1b465a1a-03bf-4625-b98…`。所以不是「hook 沒被採用」，也不是被其他 plugin 的 hook 丟掉。
- 但主 session 的正控制組三次都答「沒有」，且 CONTROL 行（從未注入）也答沒有；控制組不成立，(a) 判無效。
- 兩個子代理（`general-purpose` 與 `fankeel:fankeel-reader`）也都答「沒有／沒有」，唯一的 tool_use 是回報用的 SubagentHandback，所以是盲測；但在控制組失敗下這個答案不能解讀。
- `prompt.section` 只對引擎內建的 25 段觸發、且只在 session 開頭一次，hook 新增的段不經過它，所以它不能證明標記有沒有被送出。
- 線索（不是判定）：第三次重跑全部 10 筆 `prompt.compose` 都是 model=claude-opus-5-5、77 個 tools（5 筆真實、5 筆探針自己的呼叫）；sonnet 的 reader 回合（`turn.step` 的 agentId=aa5bdb07ffdd12507）沒有任何 reader 身分的 compose 記錄。這支持「子代理的回合不觸發 `prompt.compose`」，因控制組失敗只能當線索。
- 其他：M0 `session.start` 3 筆、command-hook 21 筆、M5 的 353 筆與記錄資料夾相符。

## 沒有量到的

從 hook 鏈的結果到模型實際收到的請求之間，記錄沒有任何觀測點。剩下兩種可能：引擎沒把 `prompt.compose` 的結果用在真正送出的請求（例如 lean trait 另有組法），或送出了但模型沒照實引用。本次分不出這兩種。M3（`agent.spawn` 改寫後 SendMessage 再送達）與 M4（`turn.step` 改 effort）沒有在這一輪判定。

## 下一輪要測

第一件事：`prompt.compose` 的結果是否進了送出的請求，例如用 `claude --debug` 的請求記錄，或在 `session.append` / `turn.step` 讀主 session 的系統提示。這一件沒答案之前，不要再跑子代理那一項。
