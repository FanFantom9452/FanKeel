# 模型分層派工實測報告：haiku 5.5 能接哪幾列、effort 該開多大、快取吃掉多少

> model-bench · 兩輪 228 次實測

## 一句話結論

派工表（`claude-ops/ops/20-dispatch.md` §4）原本把「寫腳本、審查、多來源驗證」放在 mid（sonnet）。兩輪共 228 次、全部機器門檻的實測顯示：這些列加上 agentic 修復，haiku 5.5 在有硬門檻的條件下 n/n 全過，成本是 sonnet 的 1/15 到 1/25，而且**沒有比較慢**。cheap 層的 effort 該開 **high**：比 medium 多花 15%，修掉四分之三的失誤；xhigh 零增益、時間 1.7 倍。sonnet 的 low 與 medium 無法區分。長上下文計數留 mid。每次有工具的 `claude -p` 呼叫帶約 34k token 的固定前綴，暖快取時仍佔單次成本 30–38%，所以小任務先合併再談層級。

|---|---|---|

| haiku 的 effort | medium 32/36、high 35/36、xhigh 35/36。high 每次 $0.0050（+15%），xhigh $0.0075（+73%）、中位時間 1.7×。 | 05 |

| sonnet 比 haiku 差的地方 | 七條格式約束題：haiku 三個 effort 9/9，sonnet 兩個 effort 1/6（第一行就加驚嘆號、行長超限、加逗號）。 | 04 |

## 01　研究設計：量派工表，不量模型

公開 benchmark 問「這個模型多強」；這份實測問「**我的派工表哪一列可以交給更便宜的層級**」。題目的單位因此是派工表的列，不是能力維度；評分只有機器門檻，沒有 LLM 評審；執行路徑是 `claude -p`（Claude Code harness），因為派工真正走這條路，前綴成本與快取行為只在這條路上量得到。

| 選擇 | 公開 benchmark 常見作法 | 本實測 | 為什麼 |
|---|---|---|---|
| 題目來源 | 大量自然任務 | 每題對應派工表一列，外加 4 題第五代能力 | 要改的是那張表 |
| 題數 | 數百到數千 | 12 | 每題要能機器判定、雙側校準、幾分鐘內重跑 |
| 評分 | 自動、LLM judge 或人評 | 只有機器門檻 | repo 的 gate-design 規則：閘門只裁它能判定的事 |
| 量測對象 | 正確率 | 正確率、牆鐘時間、token 組成、快取命中、成本 | 派工決策是成本／速度／品質三角 |
| 裁決輸出 | 排行榜分數 | 每列「最便宜且 n/n 全過的臂」 | 直接可寫回規則表 |

> **設計依據（repo 內）**　派工表 §2 的 answer-shape class A/B/C 決定每題門檻的嚴格度；`gate-design.md` 的 determinable-only 與兩側校準；`red-team/` 的錨點規則（引文逐字才算、捏造即整份作廢）；2026-08-16 「schema-first 契約壓抑調查本身」的量測，所以需要調查的題只給輸出契約不給步驟；`sharelib.py` 的 leak 樣式決定 fixture 不能含什麼。

每題有 **控制組**：至少一個已知應過、一個已知應不過，`bench.py selftest` 對單側缺失直接報錯。兩輪共 51 個控制組。這條規則在第一輪就抓到兩個門檻缺陷（08）。

- **high 是甜蜜點。**medium 的 4 次失誤裡 3 次是真失誤（t04 排序 ×1、t11 計數 ×2），high 把 t04 修到 3/3、t11 修到 2/3；代價是成本 +15%、中位時間 +1.2 s。

## 06　快取與成本結構

| 觀察 | 數字 |
|---|---|
| 有工具的 `claude -p` 固定前綴（system prompt + 工具 schema） | 約 34k token；無工具約 3k |
| 有工具任務每次的 token 組成（兩模型相近） | cache-read 86–98k（前綴 × 約 3 輪）、cache-write 約 10k、輸出 0.8–1.5k、未快取輸入 <10 |
| 成本組成（有工具、暖快取） | cache-read 30–38%、cache-write 44–47%、輸出 15–27%；真正的新輸入趨近 0 |
| 快取命中率 | 有工具 0.85–0.93；無工具短題 0.43–0.59；45k inline 0.01–0.02 |
| 冷啟 vs 連跑 | rep1 0.74 ／ rep2 0.73：前綴在 1 小時 TTL 內已暖；冷啟成本就是第一次的 34k × 2 倍寫入價 |
| 快取省下 | 第一輪 haiku $0.20 → $0.11、sonnet $4.02 → $1.89（全不快取 vs 實付） |
| 寫入計價 | Claude Code 寫的是 1 小時 ephemeral（`cache_creation.ephemeral_1h_input_tokens`），計 2× 輸入價；用 1.25× 算低 25%，用 2× 與 CLI 自報 228 列全部吻合到第 4 位 |
| 最貴的浪費 | t11 把 45k 帳本 inline：每次 cache-write 94k、永遠不會被讀回，佔該次成本 71%（haiku）／95%（sonnet） |

> **對派工的意義**　層級省錢（同題 sonnet ÷ haiku 10–25×），批次省更多：五個 2 秒小任務分五次派，前綴付五次；合成一次派，付一次。順序是：先合併小任務 → 再選層 → 最後才調 effort。重複派工同一大段上下文時，放檔案讓 worker 讀，或留在同一 session。同一批作業裡不要交錯 haiku／sonnet 跑同形狀任務：快取按模型分 namespace，交錯等於各付一次冷啟。

## 07　路由裁定與派工表建議

規則：取**最便宜（先層級、再 effort）且 n/n 全過**的臂為該列層級；有任何失敗即 not clean；兩層都沒全過 → escalate／redesign gate。

| 派工表列 | 原寫法 | 第一輪（n=2） | 第二輪（n=3，seeded） | 建議 |
|---|---|---|---|---|
| 摘要／重排、翻譯抽取、注入抵抗 | cheap | cheap | cheap，haiku@medium 即可 | 不變 |
| 格式契約遵循 | cheap | cheap | cheap；sonnet 1/6 | **不派 sonnet** |
| 搜尋／盤點 | cheap–mid | 升 mid 或加排序契約 | **cheap@high** 3/3；medium 1/3 | 不升層，升 effort |
| 寫腳本 | mid | 降 cheap（假設） | 降 cheap 成立 | 有硬門檻 → cheap |
| 審查／red-team | mid（異家族優先） | 降 cheap（假設） | 降 cheap 成立；4/4 植入、0 假陽性、快 3× | 接受層有錨點核對 → cheap 可接 |
| 多來源驗證 | mid | 降 cheap（門檻修正後） | 降 cheap 成立 | 本機來源 + 引文逐字核對 → cheap |
| 新：agentic 修復（tests 不可變） | — | cheap | cheap，9/9 測試 | 新增列：cheap |
| 新：長上下文 inline 彙總 | — | mid | mid，sonnet@low 即可（3/3，與 medium 同價） | 新增列：mid；禁跨派工重複 inline |
| 模糊判斷停下 | 主迴圈不可派 | 兩層都會停 | 五臂 15/15 都會停 | 不變（測的是會不會停，不是判斷品質） |

> **五條建議寫回 §4（提案，規則檔本身未被修改）**
>
> 1. **cheap 層預設 effort 改 high**（原表 cheap 列寫 low）：+15% 成本換掉 medium 四分之三的失誤，仍比 sonnet 便宜 15×。xhigh 不列入預設。
> 2. **cheap 失敗一次 → 先升 effort，再升層**：t04 的證據——medium 1/3、high 3/3；升層成本 ×15，升 effort ×1.15。前置條件：先看失誤是不是格式／排序／契約類，是的話把契約寫進 prompt 同層重派。
> 3. **多重硬格式契約的任務不派 sonnet**：haiku 9/9 vs sonnet 1/6。
> 4. **mid 層預設 effort 可改 low**：與 medium 同價、同通過數、同尾端時間（p90 都 11.6 s），low 只是不會更差。需要深推理的 mid 任務（本實測沒有）不適用。
> 5. **長上下文計數／彙總 ≥40k inline：mid**，haiku 任何 effort 都不穩（5/9）。
>

## 08　方法註記：門檻缺陷、掛住、修正

| 事件 | 怎麼發現 | 處置 |
|---|---|---|

## 09　與公開 benchmark 的設計比對

| benchmark | 量什麼 | 評分 | 借了什麼 | 沒借什麼 |
|---|---|---|---|---|
| SWE-bench Verified | 真實 GitHub issue 修復 | FAIL_TO_PASS ＋ PASS_TO_PASS，agent 看不到測試；500 題人工篩選 | 測試即門檻；測試不可被改（t10 用 sha256 鎖，比「看不到」更嚴） | 真實 repo 規模 |
| Terminal-Bench 2.0 | 終端機 agentic 任務 | 容器終態由測試腳本驗證，二元；89 題人工驗證，壓在 50% 以下 | 驗狀態不驗對話（t09／t10／t12 讀磁碟） | 難度校準到 50%：本實測要的是「cheap 能否全過」 |
| IFEval | 可驗證指令遵循 | 程式檢查 25 類約束；strict／loose | 約束全可程式判定；loose 思想（t07 放寬空白、t02 容忍 code fence） | 單約束一題：t08 故意 7 條疊加 |
| RULER | 長上下文有效長度 | 合成、長度可調；retrieval／multi-hop／aggregation／QA | 合成 ＋ seed；aggregation 題（t11） | 長度掃描：只測約 45k |
| τ-bench | 工具＋政策＋模擬使用者 | 資料庫終態；pass^k | pass^k 精神：clean = n/n；終態比對 | 模擬使用者 |
| AgentDojo | 工具 agent 注入攻防 | utility under attack ＋ attack success rate；不用 LLM judge | 同時量「任務完成」與「攻擊未成功」（t12）；零 LLM judge | 攻擊種類枚舉：只有一種注入 |
| HumanEval／MBPP | 函式級程式生成 | 隱藏單元測試 pass@k | 隱藏測試（t05） | pass@k：派工要的是 pass^k |
| GSM1k／LiveCodeBench／DyVal | 對抗題庫污染 | 隱藏配對集／時間窗／程序生成 | 程序生成 ＋ seed | 時間窗：fixture 從未公開 |

跨 benchmark 的共同趨勢與本實測的對應：驗終態不驗輸出像不像；pass^k 取代 pass@k；拒用 LLM judge；對抗污染；人工驗證題目本身——本實測用雙側控制組代替，而且第一輪就靠它抓到兩個門檻缺陷。本實測比公開 benchmark 多量的是牆鐘時間、token 組成、快取命中與成本；公開 benchmark 幾乎不報這些，而派工決策恰恰最需要。來源連結在 `DESIGN.md` 文末。

## 10　限制與下一輪

- **12 題各代表一列**，一列內部的變異（寫腳本從 20 行到 2,000 行）只採了一個點；單一注入樣式、單一上下文長度、單一語言對。
- **n=3。**公開 benchmark 用數百題換統計力，本實測用重複次數換；四個降級裁定在 n=3、seeded 下成立，但仍是小樣本。
- **量的是 `claude -p` 路徑**；Agent tool 子代理的前綴大小與快取行為可能不同，未量。
- **mid 層缺深推理題**，所以「sonnet@low 即可」只對淺任務成立。

> **下一輪**　（1）haiku@high 作 cheap 預設後，用真實派工的 process ledger 記 3 週失敗率回填 `rule-registry.md`；（2）補需要深推理的 mid 題（多檔重構、含陷阱的 API 遷移）；（3）量 Agent tool 子代理路徑的前綴與快取，確認 34k 的結論是否移植。
