# 額度在真實 limits 記錄上：7d 讀數差距的成因與 quota.js 成功路徑

結論：`quota.js` 在真實資料上走通了（dry-run exit 0、`quota.week 66`，已真寫進機器設定檔）；7d 差距在這份記錄裡看不到「讀數延遲」，看到的是同一時段有兩條各自的 7d 表（兩個 `resets_at`），但它**不能直接解釋** 09-21 那兩點差 4.7 倍。

## 7d 視窗

`node scripts/limits-series.js`（共 444 列，3 個視窗）：

```
resets 2026-10-29T04:00:00Z  261 rows  6 sessions  2026-10-28T05:19:03.017Z 21% -> 2026-10-29T00:30:00.015Z 88%
resets 2026-10-29T19:00:00Z  148 rows  9 sessions  2026-10-27T01:51:24.351Z 37% -> 2026-10-29T11:54:42.187Z 52%
resets 2026-11-05T04:00:00Z  35 rows  1 sessions  2026-10-29T04:24:03.330Z 0% -> 2026-10-29T10:49:21.367Z 20%
```

`--window 2026-10-29T19:00Z`、`--window 2026-10-29T04:00Z`、`--window 2026-11-05T04:00Z` 各印出該視窗每一列（時間、百分比、session），上面三行的起訖讀數即取自這三份。

按時間排開，各 `resets_at` 第一次出現的位置：

| 時刻 | session | seven | resets_at |
|---|---|---|---|
| 10-27T01:51 | c7256bd4 | 37% | 10-29T19:00Z |
| 10-28T05:19 | 4b267ce9 | 21% | 10-29T04:00Z |
| 10-29T04:24 | c7a97a6b | 0% | 11-05T04:00Z |
| 10-29T11:38 | 94d22511 | 51% | 10-29T19:00Z |

判斷：

- **兩組不是一個 session 中途改了重置時間。** 15 個 session 裡只有 c7a97a6b 一個換過 `resets_at`，而且是 04:00Z 跨到 11-05T04:00Z，是真的 reset。
- **是兩條各自的 7d 表交替出現。** 19:00Z 那條在 10-28T05:03 停在 51%，10-28T05:19 起換成 04:00Z 那條（21%，到 10-29T00:30 升到 88%），04:00Z 過後是 11-05 那條；10-29T11:38 本 session 又讀到 19:00Z 那條，還是 51%、之後 52%。同一段時間裡 04:00Z 那條從 21% 走到 88%，19:00Z 那條紋風不動，所以不是讀數延遲（延遲會讓 19:00Z 那條追上來，它沒有）。最合理的說法是兩個帳號或兩台機器；記錄裡沒有帳號欄，這一點只是推論。
- **跨過 reset 後從 0 起算。** 04:00Z 視窗最後一筆是 10-29T00:30 的 88%，11-05 視窗第一筆是 10-29T04:24 的 0%，隨後 1%、一路到 20%。這支持「計帳起點跟著 reset 走」，但記錄裡 reset 與第一筆之間隔了四個小時沒有讀數，起點是不是剛好在 04:00 沒法從這裡量。

回答 quota-1：09-21 的 4.7 倍來自「兩個讀數共用 `resets_at` 往前七天當起點」這個假設被排除。這份記錄補了兩件事：一、同一時段可以有不同的 7d 表同時存在，所以任何一條表上兩點相減之前要先確認是同一條；二、reset 之後確實從約 0 起算。它沒有補的是 09-21 那兩點當時是不是也是兩條表（那兩次的 `resets_at` 相同，所以大概不是）。因此 4.7 倍的成因這份記錄**沒有分出來**，只排除了「讀數延遲」在新資料裡出現。

## 還不知道的

- 兩條 7d 表是兩個帳號還是兩台機器：limits 記錄沒有帳號欄，只能從 `resets_at` 與 session 的交替推論。
- 09-21 那兩點的 4.7 倍到底是什麼：這份記錄沒有跨過同一種條件，不能回頭驗。
- 20 點的 $13.14 只來自一個視窗；`quota.week 66` 的穩定度要等下一個視窗再看。
- reset 與第一筆讀數之間的四個小時沒有資料，起算點是否正好在 reset 沒量到。
