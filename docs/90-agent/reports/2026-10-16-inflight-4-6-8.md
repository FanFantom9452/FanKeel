# `dispatch.inflight` 4／6／8 量測 — 2026-10-16

**API 這一側，8 個同時跑沒有問題：同一批 24 個 reader 從 167 秒降到 118 秒，花費不變，沒有錯誤。出問題的是 CPU 那一側：每個 agent 若各自跑整套 `node --test`，4 份同時就開始偶發紅，6 份每份紅 4–7 條，8 份有 7 份卡死；同樣 8 份、每份 `--test-concurrency=8`，2045 秒跑完、0 條紅。**

## 1. 量了什麼，沒量什麼

`dispatch.inflight`（`lib/profile.js`，預設 4，範圍 1–16）決定同一回應裡第幾個 Agent 呼叫要先問使用者（`hooks/dispatch-gate.js`）。它擋三件事：API 用量、主對話裡回來的 residue、共用 checkout 的檔案衝突。這次量兩件可以在機器上重現的事：

| 量的東西 | 怎麼量 | 代表什麼 |
|---|---|---|
| API 牆鐘與花費 | `bench.js role reader --arms sonnet --runs 2 --jobs 4/6/8`，12 題 × 2 輪 = 每組 24 個 `claude -p` | N 個 reader 同時讀 |
| CPU 負載與偶發失敗 | `suites.js`：k 份整套 `node --test` 同時跑，每份在自己的 worktree | N 個 verifier／implementer 同時跑 suite |

**沒量**：主對話的 residue。`claude -p` 每次是獨立 session，量不到「同一回應 N 個 Agent 回來後主對話多了多少」。那個數字要在真的 session 裡量，這次沒做。

機器：AMD Threadripper，64 核 128 執行緒，128GB，Windows 11。Node 回報 `availableParallelism` = 64（它看的是一個處理器群組），但實測執行緒會排到全部 128 個邏輯處理器上，所以不是限制。

## 2. API 側：reader 4／6／8

| jobs | 24 個 run 的牆鐘 | 每個 run 牆鐘（中位數／最大） | 通過 | 錯誤 | 花費（`claudeUsd` 合計） |
|---|---|---|---|---|---|
| 4 | 167 秒 | 16／26 秒 | 24/24 | 0 | $0.412 |
| 6 | 137 秒 | 17／22 秒 | 23/24 | 0 | $0.387 |
| 8 | 118 秒 | 17／22 秒 | 23/24 | 0 | $0.355 |

- 單一 run 的牆鐘不隨寬度變長，所以 8 個同時沒有碰到 API 的速率限制。總牆鐘的縮短接近寬度的比例（4→8 省 29%，題目只有 24 個，第二波沒填滿）。
- 6 和 8 各掉的那一題是同一題（`easy-who-requires` 第 1 輪，答成 `signup.js` 而非 `lib/signup.js`），是 reader 的答案錯，跟並行無關。
- 花費三組差不到 15%，每組只跑一批，這個差距在雜訊內，不讀成趨勢。花費是 bench 依 token 計價的結果，這裡沒有另外列 token 數。

## 3. CPU 側：整套 suite 同時跑 k 份

| 組 | 每份 worker 數 | 總牆鐘 | 每份平均佔用 | 每份紅幾條 | 結果 |
|---|---|---|---|---|---|
| k1 | 預設（63） | 287 秒 | 287 秒 | 0 | 基準 |
| k4 | 預設 | 1085 秒 | 271 秒 | 1、2、3、4 | 全部跑完 |
| k6 | 預設 | 1642 秒 | 274 秒 | 6、6、7、6、6、4 | 全部跑完 |
| k8 | 預設 | — | — | 跑完的那份 15 條 | **8 份裡 7 份卡死**，人工停掉 |
| k8c8 | 8 | 2045 秒 | 256 秒 | 0 ×8 | 全部跑完 |

「每份平均佔用」＝總牆鐘 ÷ 份數。四組都在 256–287 秒，代表**單份 suite 用預設並行就已經把機器吃滿**。同時多跑幾份，總工作量不會更快做完，只是每條測試變慢：k4 的測試耗時合計是 k1 的 4.6 倍（每份 22,401 秒對 4,844 秒）。

慢了以後，有逾時的測試就會紅。`failing-under-load.txt` 列出 k4、k6、k8 紅過的測試；最常紅的幾條都在量時間：

- 「a process that probes a station exits on its own within 3 seconds」
- 「the first run scans once and records that it did」
- 「a station whose own event loop is blocked is busy, not dead」
- 宣告與存活檢查（collisions）的幾條

131 條紅裡只有 18 條標了 `@slow`。所以這天稍早「10 條 @slow 紅、重跑全綠」講的是同一件事：紅的原因是負載，不是測試本身，而且大部分紅的測試沒有標 `@slow`。

### k8 為什麼卡死

8 份同時起跑時，約 504 個測試 worker 幾乎同時在生子行程。15:43:45–47 這 3 秒裡生出的 11 個 node 子行程（`orient.js`、`docs-check.js`、`ledger.js`、`judge.js record`，以及 `inject`、`gate`、`brief`、`gate-write`、`leave` 五個 hook）啟動後就停住了：

- 每個只用了 0.3–0.4 秒 CPU，大約是 node 開機的量
- 每個只有 4 條執行緒
- 沒有生出任何子行程

停住之後的 3 小時都沒有再動，那段時間 CPU 只有 2–9%。測試用 `execFileSync` 呼叫這些子行程，沒有設 `timeout`（例如 `tests/orient.test.js:30`），`node --test` 預設也沒有單一測試逾時，所以子行程一停住，那份 suite 就永遠等下去。子行程為什麼會在啟動時停住，這次沒查到根本原因；已知的是它只出現在同時生行程最密的那幾秒。

k8c8 的總 worker 數是 64，跟單份預設差不多。它沒有卡死、沒有紅，每份平均佔用也是四組裡最短的。

## 4. 結論與建議

1. **只讀的 dispatch（reader、reviewer）可以把 `dispatch.inflight` 開到 8。** API 側沒有限制，牆鐘明顯縮短。真正的成本是每個回來的答案都留在主對話裡；這次沒量，所以 6、8 只建議用在答案短的 fan-out 上。
2. **會跑 suite 的 agent（verifier、implementer），開多少個要看 CPU。** 這台機器上，整套 suite 一份就吃滿 CPU。多個同時跑時，總 worker 數要壓在約 64：每份 `--test-concurrency` ≈ 64 ÷ 同時份數。不壓的話，4 份就開始偶發紅，8 份會卡死。`scripts/suite.js` 的機器鎖（`lib/suitelock.js`，同一時間只跑一份）是另一種解法：安全，但更慢。
3. **`dispatch.inflight` 只控制同一回應裡派幾個 agent，不控制它們各自跑幾個測試行程。** 第 2 點要靠 suite 的並行設定，不是靠這個鍵。

## 5. 留下來的問題

- 測試裡的 `execFileSync` 沒有 `timeout`，子行程一停住整份 suite 就停住。這是可以修的缺陷，應該開成 TODO。
- 子行程在大量同時生行程時，為什麼啟動就停住：根本原因未查。
- 主對話 residue 在 N=4／6／8 時的曲線：未量。
