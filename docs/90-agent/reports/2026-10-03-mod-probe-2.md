# prompt.compose 的結果有沒有進送出的請求 — 2026-10-03 的量測：進了，模型也讀得到（拋棄式探針，n=1）

這一頁接 `2026-10-03-mod-probe.md` 的「下一輪要測」第一件事。結論先講：mod 在啟動時就啟用的情況下，`prompt.compose` 的結果進了送出請求的 system 區塊，模型也照實引用。所以上一輪的控制組失敗，不是引擎不採用 compose 的結果。探針與 proxy 都是拋棄式（throwaway）的，跑完不維護。跑一次就不再更新。

## 方法

- Claude Code 2.1.288，headless（`claude -p`）。上一輪的 mod 複製到 `probe2/mod`，記錄路徑指向 `probe2/records`，用 `--plugin-dir probe2/mod --settings probe2/settings.json` 載入；`settings.json` 把 `enabledPlugins` 的 `fankeel-mod-probe@inline` 設為 true。
- `debug1.log` 沒有附上：使用者的 settings.json 把該 plugin 設為 false，log 只有 `Loaded inline plugin from path: fankeel-mod-probe`，沒有 `Loading hooks from plugin: fankeel-mod-probe`，也沒有任何記錄，模型答沒有／沒有。所以 mod 是啟動時啟用，不是熱重載。
- `debug2.log`：`--debug-file`，不經 proxy。`debug3.log`／`debug4.log`：把 `ANTHROPIC_BASE_URL` 指向 `http://127.0.0.1:8899`，由 `proxy.js` 把請求本文存下來（核准的計畫裡的備案）。debug3 有 mod，debug4 沒有 mod。

## 結果

- `--debug` 看不到請求本文：`debug2.log` 的 `grep -c MOD-PROBE` 是 0。它只有第 147 行 `hooks module fankeel-mod-probe@inline loaded`、第 362／397 行 `compose returned ids=lean_body,fankeel-mod-probe:marker-shared,...`、第 408 行 `[API REQUEST] /v1/messages ... source=sdk`，仍然只是 hook 鏈的結果。這一路回答不了問題，所以改走 proxy。
- 有 mod（`request-bodies-with-mod/1791007909248-1.json`，model claude-opus-5-5）：nonce 標記 `MOD-PROBE-COMPOSE-1b465a1a-03bf-4625-b98b-641da37268c9`（與 `records/` 的 `prompt.compose.after` 相符）與 `MOD-PROBE-COMPOSE-SHARED-` 標記都在 `system[2].text`，不在 `system[0]`、`system[1]`。`messages` 裡只有提問自己的文字（`MOD-PROBE-COMPOSE-` 前綴與 `MOD-PROBE-CONTROL-`），完整 nonce 不在 messages。
- 模型引用了 COMPOSE 行與 nonce，且與記錄相符；CONTROL 行答沒有。`debug2` 那次（第二次有 mod 的執行）同樣答對 nonce、CONTROL 答沒有。
- 沒有 mod（`request-bodies-no-mod/1791007938627-1.json`、`debug4.log`）：本文中 nonce 的 `grep -c` 是 0，`system[2]` 沒有標記，模型答沒有／沒有。所以 proxy 這條偵測在標記存在時看得到、不存在時看不到。
- 控制組規則（`plans/2026-10-03-mod-probe-design.md:37`）成立：引用的 nonce 與記錄相符，CONTROL 答沒有。

## 結論

啟動時啟用的 mod，`prompt.compose` 的結果會進送出的請求（system 區塊）、模型讀得到。所以 `2026-10-03-mod-probe.md` 的控制組失敗不是「引擎忽略 compose」。與上一輪最可能的差別是啟用路徑（session 中途熱重載）；這只是假設，沒有測：這一輪在 headless `-p` 下做不到熱重載。
