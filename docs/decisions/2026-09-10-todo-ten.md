# TODO 十條一次清 — 決策

使用者的問題是「TODO 還有哪些沒做，可以一次做完」。`## Ready` 一條與 `## Needs a
decision` 九條，每條在 design 閘門各問一次，九題都取推薦選項。這份記的是每個答案
為什麼是那個，以及建到一半被程式碼推翻的東西。

## 九個答案

- **第三個 agent 是 `fankeel-reviewer`，不是給 reviewer 傳 model。** build 的 per-task
  reviewer 與 verify 的 adversary 問的是同一種問題——這份 diff 或這張表哪裡不成立——
  而 reader 問的是檔案說了什麼。工具表一樣，差別在問題的形狀，所以是一個檔案兩個
  派遣者。model 釘在 agent 檔裡，dispatch 端不再手打。
- **exact-set 推廣到 `skills/` 與 `hooks/`。** 名單寫死在 `tests/inventory.test.js`，
  多一個目錄或 hook 檔就紅、紅的訊息說出名字；從目錄產生名單的測試什麼都擋不住。
- **`skills/registry.json` 只放能從程式碼推出來的欄位。** entry condition 取
  `Read the fankeel-<stage> skill on entry:` 那句、stop condition 取 skill 的
  `Done when`、bytes 取 `lib/render.js` 的實際輸出、budget 取 `lib/stages.js` 新加的
  `budget`；整檔由 `scripts/stage-registry.js` 重寫，所以沒有一條規則能寫在那裡。
- **build 的停止條件改成「撤掉會不會變差」。** 四個 stopper 不變，判準變成 git 回不
  回得來；能 revert 的一切都豁免。同一次改寫加了 reachability test：每條規則都要到
  得了注入 block，藏在沒開的 `when` 後面就紅。
- **design class 不做。** mockup 步驟已在 0.58.0 落地，其餘是另一個 architectural
  任務；entry 移到 `## Waiting`，plan 檔留著不封存。
- **六條通道補進 provenance.txt，腳本一行不改。** 數字是舊腳本跑的，改腳本會讓紀錄
  對不上它描述的那次執行。
- **ALWAYS 只加一句，不加第五條。** `tests/render.test.js` 釘著條數；「constraint 贏、
  shape 留」掛在第三條句尾，四條的成因表放在 `skills/fankeel/SKILL.md` 的
  `## Calibration`。
- **四個 eval case，成對跑不做。** `route-typo` 自己的分數還在跳，「分數不該動」的判
  準量不出東西；每個 case 至少一個 `max: 0` 的反向 grader，讓分數有路可以掉。
- **新 role `fixture`。** eval 文件不描述系統，只驗連結；`docs-check` 的符號與引文
  檢查只對 `reference` 做，所以不用新分支，只要 `lib/docs.js` 認得這個字。

## 程式碼推翻了設計的兩句話

audit 的 pair reader 開的。設計 §10 寫「一條規則兩個檢查」，`blockers()` 裡其實是兩
個獨立述詞：`isLive`（`lib/guard.js:130`）對每個持有者都問，`claimedFirst`（`:131`）
只在自己也持有時問。設計 §1 寫 `SubagentStart` 的 payload 只有 `agent_id` 與
`agent_type`、agent 檔是 `dispatch.floor` 唯一被 harness 執行的釘點——
`hooks/brief.js:36` 讀 `session_id`，而檔裡釘的是字面 `sonnet`，沒有東西讀
`dispatch.floor`。兩句都在 cleanup 改掉。design 的閘門通過的是意圖，不是對程式碼的
斷言；斷言要等 audit。

## 建到一半才知道的事

- **headless transcript 裡派 subagent 的工具叫 `Task`——這條是錯的，2026-09-11 推翻。**
  當時讀的是 eval JSON 裡子 session 的 system-init `tools` 陣列，裡面有 `Task` 沒有
  `Agent`。那個陣列是這個 session 被提供了哪些工具，不是一次派工被記成什麼，而
  `type: tool_used` grade 的是後者。三個 grader 因此在 `15daa59` 被改成 `Task`，
  改錯了：兩份 CLI 2.1.267 的 transcript 裡真實派工都記成 `Agent`，這台機器上沒有
  任何一份 transcript 出現過 `"name":"Task"`。`fc937c6` 改回 `Agent`，經過寫在
  `docs/reports/evidence/2026-09-10-exception-cases/provenance.txt`。
- **reachability test 會替沒人有的 `when` 鍵造值。** 一條規則掛在 profile 沒有的鍵
  上，測試合成那個值就綠了；加一條斷言，鍵必須在 `lib/profile.js` 的 `KEYS` 裡。
- **agent 檔在行程啟動時載入。** 寫出 `fankeel-reviewer` 的這個 session 派不到它；
  cleanup 的 review 由 `fankeel-reader` 帶 reviewer 的 template 頂替，裁定記在 ledger。
  設計的 Unverified 那條倒是量到了：dispatch 端不傳 model 時，跑的是 agent 檔釘的。
- **plan 的 stage rule 改成 `fankeel-reviewer` 時，plan 的 skill 沒跟。** 同一條分支
  的 Task 3 改了 `lib/stages.js:280`，skill 第 5 步還叫人手打 `sonnet`；到 audit 才
  由 adversary 發現，三處列舉從兩個派遣者改成三個。
- **`lib/stages.js` 插行，四支 skill 十五條引用位移。** 上一次是十一條。照 `docs-check`
  印的新行號改，再用它驗。
- **四個 case 首跑（opus）正向 grader 全掉。** 是 prompt 沒逼出行為、grader 太窄，
  還是模型——沒有答案，進 `## Needs a decision`。
