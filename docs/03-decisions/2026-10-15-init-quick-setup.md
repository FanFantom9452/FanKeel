# 新專案的設定，從聊天裡的 init 開始（10-15）

一句話：新專案先在聊天裡跑 `/fankeel-init`，第一步就問開發習慣，一鍵套用建議值；接著問一次要不要整理 docs，說好才做；監控站的習慣卡留著，給事後調整用。

## 決定

- init 的順序改成：先問開發習慣（第 1 步），再問一題要不要整理 docs（第 2 步），回答「整理」才進文件的幾步（第 3–8 步）。
- 習慣那一題有四個選項：建議值（平衡）、省 context、每關都問、逐項設定。前三個各是一行 `task.js profile preset <名稱>`，一次寫完；逐項設定照監控站習慣卡的順序一題一題問。
- 選「建議值」時，收尾要 merge 還是開 PR、要不要 push，先看這個 repo 的 git 歷史；寫到整台機器的預設時不看歷史，因為那不是某一個 repo 的習慣。
- 整理 docs 的問題有三個答案：整理、先不要（寫 `init.skip true`，開任務時不再提醒）、下次再說（什麼都不寫，下次開任務還會提醒）。
- 監控站習慣卡的「省 context」改成把每一站都交給站 agent，跟 `PRESETS.lean` 一樣。

## 為什麼

使用者在 10-15 把監控站上作答關掉，所有問題都要在聊天裡問；init 是唯一在聊天裡問、也知道專案文件狀態的入口。原本有四個地方各自問「新專案怎麼設」，同一個名字「省 context」在兩處寫的值不同。把開發習慣和整理文件拆開，是使用者自己要的：習慣幾秒鐘就能設完，整理文件比較久，要先問。

## 放棄了什麼

- 以監控站頁面當入口：跟使用者關掉網頁作答的做法相反，而且頁面拿不到 docs.json、TODO 這些 init 才有的資訊。
- 只改介面、不動鍵和預設：「省 context」同名不同值的矛盾會留著。
- 跳過整理 docs 要確認兩次：改成一題，跳過的代價寫在「先不要」的說明裡。
