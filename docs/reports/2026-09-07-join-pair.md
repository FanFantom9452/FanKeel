## 4. 結論

**這一對量到 11.46× 的 residue 優勢，是四對裡最大的一次，而且是第一次 dispatch 同時比較便宜（0.95×）也比較快（0.56×）。** 但這句話不能單獨拿去跟任一個既有對照組比，因為沒有一個既有對照組只差「一人一頁＋diff」這一個變數：

- 跟第二對（1.52×，命名、無 join、四個讀者依 lens 分工）比，本對同時換了兩件事——一人一頁（不是分工）、外加 diff（不是只給頁面本身）。
- 跟第三對（2.55×，命名、join 在、四個讀者依 lens 分工）比，本對同樣同時換了兩件事——一人一頁、外加 diff。

換句話說：**11.46× 是「一人一頁」和「多一個來源」兩個變數一起買到的，這一頁沒有辦法把兩者拆開，跟第三對自己能拆出「命名」與「join」兩個單變數效果不是同一件事。** 要拆開，需要再跑至少一對只換其中一個變數的對照組——這是 §6 留下的洞，不是本對回答的問題。

**機制上能講清楚的一半，是為什麼 residue 漲得比第三對更多，而 turn 數沒有多漲。** 第三對的 inline arm 是 9 個 turn、160,728 tokens；本對的 inline arm同樣是 9 個 turn，residue 卻是 517,009——turn 數完全一樣，residue 卻是 3.2 倍。第一對到第三對的機制是「要找東西的 turn 更多」（13 turn 對 9 turn）；本對的多出來的 residue 不是來自更多 turn，是**同樣 9 個 turn、每個 turn 裝的東西更重**——`usage.output_tokens_details.thinking_tokens` 是 23,373，佔 output_tokens 的 93%，這是要把 722 行的 diff 逐一比對五個頁面才需要的推理量，而第三對沒有這一步。

**為什麼 dispatch 這次反而比較省：** dispatch 的五個 subagent 平行跑，各自只需要讀自己的一頁加同一份 diff（不必像 inline 那樣在一個 session 裡輪流切換五個頁面、每次都要把前面讀過的重新帶進 context），所以 wall-clock 由最慢的那個 subagent 決定，而不是五個頁面依序疊加；錢上, subagent 用的是便宜的 `sonnet`（426,355 tokens／US$1.0096）,真正燒錢推理的那一步被搬去便宜的 model 上做,inline 唯一的 session 全程掛在貴的 `opus` 上做同一件事（542,197 tokens／US$1.6211）。這跟前三對「工作量一小,dispatch 的固定開銷佔比就變大」的機制正好相反——這一對的工作量夠大（五個頁面各自要跟 722 行 diff 比對）,固定開銷被攤薄了。

## 5. 這一對量測本身的陷阱與觀察

**(a) `duration_ms` 這次兩邊表現不同，再次證明它不可信。** Arm A 的 `duration_ms` 是 9,165 ms,而 `shell_seconds` 是 202 秒（202,000 ms）——低報 22 倍，比前三對量到的任何一次都誇張。Arm B 的 `duration_ms` 是 354,396 ms,`shell_seconds` 是 361 秒（361,000 ms）——這次幾乎吻合，只差 1.9%。同一個欄位在同一對量測裡,dispatch 臂嚴重低報、inline 臂幾乎準確，這正是為什麼 wall-clock 必須從 process 外面用 shell 量，不能信 JSON 自報的欄位。

**(b) 「一人一頁＋diff」這個形狀有一個結構性的盲點，而這一對的答案密度差異就是證據。** dispatch 的五個 subagent 每個只看得到自己的頁面加 diff,看不到其他四個頁面;inline 的單一 session 五個頁面同時在 context 裡。Inline 找到的十個發現裡，至少三個（`skills/fankeel-design/SKILL.md:122`、`:125`、`docs/subagents.md:136`）講的是**這個頁面被另一個頁面的內容（不是被 diff 本身）推翻**——例如 `skills/fankeel-design/SKILL.md:122` 那一行是被 `skills/fankeel-plan/SKILL.md:129` 與 `docs/subagents.md:40` 推翻的，不是被 diff 直接推翻的。一個只看得到自己頁面加 diff 的 subagent,結構上就看不到這種跨頁矛盾——dispatch 臂五個頁面裡有四個回報「no finding」,不代表那四頁真的沒有東西可挑，可能只是這個方法形狀本來就挑不到跨頁的那一種發現。這不是說 dispatch 這次的答案是錯的（§2c 核對過那一個發現是對的）,是說這個方法形狀的**涵蓋範圍**跟 inline 不同，不只是「同一批發現、換一種方法拿到」。

**(c) 兩邊的回答密度差了 4.4 倍（371 字對 1,628 字）,但兩邊都不是空轉。** §2c 已經核對過四個錨點，全部對得上真實檔案內容。密度差異本身值得記下來，但不足以判斷哪一邊的答案「比較對」——這一頁量的是 token、錢、時間，不是答案品質的裁判。
