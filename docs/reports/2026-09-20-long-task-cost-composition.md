# 長任務的成本成分 — 2026-09-20

**成本成分會隨任務長度移動，所以短任務量到的「換模型省多少」不能外推到長任務。** 把 94 筆可定價 session 按 request 數分成四桶：cache write 從 44.5% 掉到 20.2%，cache read 從 31.0% 升到 61.4%，主 session 的占比從 72.9% 掉到 59.4%。只看 `F:\ymlab\fankeel` 一個專案的 78 筆，同一個方向仍然成立（46.7% → 21.8%、28.7% → 57.0%、69.2% → 53.8%），所以這不是四個 registry 的組成差異造成的。

這份報告回答的是 [decisions/2026-09-20-survey-brain.md](../decisions/2026-09-20-survey-brain.md) 第三節留下的一個範圍問題：那一節的 A/B 全部是 survey 一站、六到十四輪的短任務，而使用者實際跑的 `architectural` 任務會在 build↔verify↔audit 之間來回，context 曾經到過 860k。兩者的成本長相不一樣。

## 3. 移動的是什麼

**cache write 換成 cache read。** 短任務每一輪都在寫新的快取；長任務寫過的東西被讀很多次。`lib/prices.js` 裡 5m 寫是 input 的 1.25 倍、1h 寫是 2 倍，而讀是 input 的 1/10（opus：input 5、cacheRead 0.5、cacheWrite5m 6.25、cacheWrite1h 10，每百萬）。所以同一筆 token，寫進去一次很貴、讀出來很便宜——長任務的便宜之處就在這裡，而它的貴之處是讀的次數。

**output 的占比反而在降**（24.4% → 18.4%）。長任務不是寫出更多字，是重讀更多東西。

**主 session 的占比在最長那一桶掉到 59.4%**，因為長任務會派出大量 subagent。最大的一筆是 `session e0e4ea99`，7,056 個 request、$781.25，其中 $390.35 是 subagent 的。

## 5. 這不是 A/B

五件事會限制這一頁能說什麼，逐條寫在這裡而不是留給讀者推：

- **沒有對照組。** 94 筆全部是舊模式（主控一路走到底），沒有一筆是 survey 大腦模式。所以這一頁量的是「長任務的成本長什麼樣」，不是「換了模式之後長什麼樣」。
- **桶是觀察，不是分派。** 沒有人把一個任務隨機指定到某一桶；長任務之所以長，本身就是因為它難。成分與長度的關聯在這裡是相關，不是因果。
- **樣本偏向一個專案。** 94 筆有 78 筆是 fankeel 自己，第 4 節的控制只能說明「桶間差異不是專案差異」，不能說明別的 repo 也是這個比例。
- **有 7 筆帶著定不了價的模型。** 表上 `unpriced` 欄寫 `<synthetic>` 的那幾筆，那個模型不在 `lib/prices.js` 裡，它的 token 完全沒有被計入——沒有當成 0 元混進去，但那幾筆的總額是偏低的。
- **版本只涵蓋最後幾天。** 94 筆裡只有 34 筆帶 `version`（0.72.0 四筆、0.73.0 三筆、0.74.0 二十七筆），其餘 60 筆是這個欄位存在之前寫的。要按版本比較成本，得等資料累積。

## 6. 對第三節的意義

[decisions/2026-09-20-survey-brain.md](../decisions/2026-09-20-survey-brain.md) 第三節說換模型之所以只打平、沒變便宜，是因為主控沒有變短而又多付一整個 Opus 大腦的 context。那一段在它自己的量測範圍內是對的，這一頁不推翻它——只是把範圍寫清楚。

那一節的 A/B 落在 `<50` 這一桶附近，那裡 cache write 佔 44.5%、主 session 佔 72.9%。七站來回的任務落在 `800+`，那裡 cache read 佔 61.4%、主 session 只佔 59.4%。**「換模型省的是什麼、值多少」在兩端不是同一件事**：短任務省的是寫快取，長任務省的是讀快取，而 Sonnet 對 Opus 在每一個成分上都恰好是 0.4 倍（`lib/prices.js`），所以沒有哪一個成分是換模型特別划算或特別不划算的——會變的只有「哪一邊的量比較大」。

要真的變便宜，仍然得讓其中一邊真的縮短。這一頁沒有回答那個問題，它只是把問題問對了位置。

## 7. 怎麼自己重跑

```
node scripts/spend.js              # 全機器，discover 找到的每一個 registry
node scripts/spend.js --root <dir> # 只看一個
```

站台首頁的分段控制也加了 `依成分` 與 `依版本` 兩格（[station.md](../station.md)）。**本頁的總額比站台小，差在覆蓋範圍，不在算法。** 這一點量過：在這個 repo 的 registry 上，91 筆同時有 `usage` 與 `days[].usd` 的，兩邊逐筆到分相同；其中 78 筆也有 `spend` 的，`stages[].usd` 的總和也逐筆相同。三個欄位是同一個量測，差別只在誰有——`days` 只要有 transcript，`usage` 在 session 結束時才寫，`spend` 則只有 2026-09-07 之後結束的 session 才有——比加它的 commit 晚兩天，不是程式碼落地那天。所以本頁只能為全機器 311 個 session 檔裡的 94 個定價，而首頁能為每一個有 transcript 的定價。（上面那組逐筆比對只跑這一個 repo 的 registry：179 個檔、78 個帶 `spend`。兩組數字分母不同，別混著引。）
